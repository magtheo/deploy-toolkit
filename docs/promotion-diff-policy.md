# Promotion Diff Policy

The human gate is a PR. The PR's authority comes from what it changes — so
what it is allowed to change is the invariant. This is a **semantic** policy,
not a path allowlist: restricting paths alone would still permit a target
swap inside an allowed file.

## The rule

A promotion PR may contain exactly:

1. **One added immutable release file**
   `.deploy/releases/<project>-<version>.yaml`
   - canonical filename, generated by `release create`;
   - filename must agree with the manifest (`metadata.project`,
     `metadata.version`);
   - OR no added file, if the target release file already exists unchanged
     (e.g. rolling back to a previous release).
2. **One modified environment file**
   `.deploy/environments/<environment>.yaml`
   - **only `spec.release` may differ** from the trusted base version;
   - `metadata.name`, `spec.target`, `failurePolicy` and everything else must
     be semantically identical;
   - `spec.release` must point at exactly the release file above;
   - `from ≠ to` (a no-op diff means the proposal is stale and must be
     regenerated against the new trusted base).

Nothing else. Any other added/modified/removed file fails the check. Existing
release files under `.deploy/releases/` are immutable — modifying or removing
one always fails.

## Compare-and-swap semantics

The environment change is a CAS operation:

```
ONLY change:  production = OLD
TO:           production = NEW
IF:           production still == OLD
```

The PR diff is computed against the live trusted base. If another promotion
merges first, the diff collapses to a no-op or a mismatch and the policy fails
it. Stale proposals are regenerated deliberately — never quietly re-based.

## Execution from trusted code

The check must run from code the PR cannot influence: the toolkit's reusable
workflow, pinned by full commit SHA, executing `deployctl promotion check
--repo <repo> --base <base-sha> --head <head-sha>` against base/head trees via
the GitHub API. It never executes PR-controlled code and needs no production
secrets.

## What propose guarantees at creation

`deployctl promotion propose` builds compliant commits by construction:

- the proposal branch is cut from the **trusted branch head** (`main`), not a
  caller-selected ref;
- the release manifest is re-verified against **current** eligibility policy
  (fresh `Evaluate`: ancestry, checks, artifact digests, bundle and contract
  digests) and must byte-match what current eligibility would generate —
  evidence fields cannot drift between `release create` and promotion;
- the commit contains exactly the two entries above, created through the Git
  data API as **one atomic commit**;
- proposal creation is idempotent: an existing open proposal for the same
  environment → same target returns the existing PR; a different open
  promotion for the same environment fails with the conflict named.

What propose deliberately does **not** guarantee: the `version` and
`migration.*` fields are explicit human claims, not derived evidence — they
are re-rendered from the release manifest itself, and the PR body surfaces
them for review. The human merge remains the authority transition.
