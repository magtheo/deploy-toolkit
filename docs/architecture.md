# Architecture

Deploy Toolkit is a **release-promotion and deployment engine**. It takes an
immutable release and makes it the state of an environment, behind a human
authorization gate.

## The three control planes

Deploy Toolkit deliberately does not do everything. It sits between change
control (CI Toolkit) and infrastructure (Pulumi), and the application declares
its own deployment contract:

```
               SOURCE / CHANGE CONTROL
                       │
                  CI Toolkit
                       │
               Human merge to main
                       │
                       ▼
                 immutable release
                       │
                       ▼
              ┌─────────────────┐
              │ Deploy Toolkit  │
              │                 │
              │ release         │
              │ promotion       │
              │ deployment      │
              │ rollback        │
              └────────┬────────┘
                       │
                deployment target
                       ▲
                       │
                    Pulumi
                       │
                infrastructure
```

| System             | Fundamental question                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| **CI Toolkit**     | *Should this change be allowed toward `main`?*                               |
| **Deploy Toolkit** | *Should this release become the state of this environment, and did it work?* |
| **Pulumi**         | *What infrastructure should exist for that environment?*                     |
| **Your app**       | *What application are we actually running?*                                  |

CI Toolkit and Deploy Toolkit **do not depend on each other**. Both meet in the
consuming repository:

```
ci-toolkit
     ╲
      ╲
       example-service
      ╱
     ╱
deploy-toolkit
```

## Vocabulary

| Concept                 | Meaning                                                  |
| ----------------------- | -------------------------------------------------------- |
| **Project**             | Something that can be deployed, e.g. `example-service`   |
| **Release**             | Immutable application version + artifacts                |
| **Environment**         | Desired deployment state, e.g. `production`              |
| **Target**              | A machine/environment capable of receiving a release     |
| **Deployment Contract** | Project-specific instructions for applying a release     |
| **Promotion**           | Human authorization to make an environment use a release |
| **Deployment**          | Attempt to make the target match that promoted state     |
| **Observed State**      | What the target is actually running                      |

The most important distinction:

```
Release ≠ Deployment
```

```
release:
    example-service @ abc123

deployments:
    staging     → abc123
    production  → 7fd981
```

A release can exist without ever reaching production.

## The immutable release

A release is not just a git commit. One canonical manifest pins:

- the source commit;
- the exact artifact digests;
- the runtime bundle digest;
- the deployment-contract digest;
- the migration semantics.

```yaml
apiVersion: deploy.toolkit/v1
kind: Release

metadata:
  project: example-service
  version: 0.1.17

source:
  type: github
  repository: example-org/example-service
  revision: abc123def456...

artifacts:
  app:
    type: oci
    image: ghcr.io/magtheo/main
    digest: sha256:aaa...

bundle:
  digest: sha256:ddd...

deploymentContract:
  digest: sha256:eee...

migration:
  head: "043"
  mode: forward-compatible
  rollbackSafe: true
```

There is **no `latest`**. OCI `image`/`repository` fields are untagged
repository names; the digest is the only pointer. Releases are normally
generated by `deployctl release create`, not hand-written.

The deployment bundle is built deterministically from the exact Git tree at
the release revision — see [bundle-format-v1.md](bundle-format-v1.md) for the
canonical tar rules and the precise digest definitions.

## Repository layout of a consumer

```
.deploy/
├── project.yaml                  deployment contract (from the release)
├── releases/
│   ├── my-app-0.1.15.yaml
│   ├── my-app-0.1.16.yaml
│   └── my-app-0.1.17.yaml
└── environments/
    └── production.yaml           human-approved desired state
```

Promotion is a one-line diff of `spec.release`; rollback is the same diff in
reverse.

## Push, not pull

V1 uses a **push** model: GitHub deploys to the server over SSH.

- no daemon and no polling;
- no GitHub credentials on the server;
- easy bootstrap, obvious execution boundary.

A pull/agent model may be earned later by many hosts, not before.

## Target interaction primitive

Deployment semantics are written once, above a small transport boundary:

```go
type Transport interface {
    Put(ctx context.Context, req PutRequest) error
    Run(ctx context.Context, req RunRequest) (RunResult, error)
}
```

- `Put` transfers exact bytes to an absolute destination path with an explicit
  file mode (atomic write, parent directories created); relative paths and
  `..` traversal are rejected.
- `Run` executes an **argv vector** with an explicit working directory and
  explicit environment (nil inherits; a map replaces wholesale). stdout and
  stderr are captured separately, the exit code is preserved, and context
  cancellation kills the process. A non-zero exit is a command *result*, not
  a transport error.

`local` (V1, deterministic integration tests) and `ssh` (V1, strict host
verification) implement the same contract; the deployment state machine never
knows which one is underneath.

The SSH implementation notes:

- **Mandatory pinned host key** — an OpenSSH public host key line
  (`ssh-ed25519 AAAA...`) is verified exactly on every connection; there is no
  code path equivalent to `InsecureIgnoreHostKey`.
- **Put uses SFTP** — same-directory temp file, chmod, sync, atomic rename;
  exact bytes and Unix mode.
- **Run encodes argv deterministically** — SSH's exec request carries a
  command string, not an argv vector, so the transport renders
  `cd '<dir>' && exec env -i 'K=V' … 'argv0' 'args…'` through one tested
  POSIX single-quote encoder. The shell underneath is an implementation
  mechanism, never an interpretation mechanism: supplied values remain data.
- SFTP fsync is requested and tolerated only when the server declares the
  `fsync@openssh.com` extension unsupported; every other sync error fails
  closed.

## Two trust stages per deployment

```
prepare (no production secrets)
├── verify release
├── checkout promoted source SHA
├── construct deployment bundle
├── validate checksums
└── upload temporary deployment artifact

deploy (only the target connection credential)
├── DO NOT checkout application source
├── download verified deployment bundle
├── verify bundle digest
├── SSH target
├── stage → apply → verify
└── record state
```

Production application secrets never enter GitHub at all. They live on the
target, outside the release.

## Server filesystem model

Releases are environment-independent; state and history are
environment-scoped. All paths live under the Target manifest's
`spec.deployRoot` (see `docs/target-state.md`):

```
<deployRoot>/<project>/
├── releases/
│   ├── 0.1.15/
│   ├── 0.1.16/
│   └── 0.1.17/                ← .staged.json marks the complete stage
├── state/
│   └── <environment>.json     observed state ("current" advances only after verification)
└── history/
    └── <environment>.jsonl    append-only, integrity-checked hash chain

/etc/<project>/
└── production.env             application secrets (outside the release)
```

## Desired vs observed state

Git owns desired state; the target owns observed state:

```json
{
"project": "example-service",
  "environment": "production",
  "release": "0.1.17",
  "sourceRevision": "abc123...",
  "deployedAt": "...",
  "health": "healthy"
}
```

- `desired == observed` → healthy
- `desired != observed` → drift (e.g. after an emergency rollback, before Git is reconciled)

Lightweight GitOps without a reconciler.

## Targets and Pulumi

A target is intentionally boring: "can Deploy Toolkit establish a trusted
connection and execute the deployment protocol?" No cloud-provider fields —
those belong to Pulumi, which can later emit a Target descriptor as an output.

```
                  Platform Operator
                         │
              ┌──────────┴──────────┐
              │                     │
            Pulumi            Deploy Toolkit
              │                     │
        provision tenant       deploy version
              │                     │
              └──────────┬──────────┘
                         ▼
                       Tenant
```

Multi-tenancy later means more environments and more targets — the
release/deployment separation stays intact.

## What is deliberately not built (v0.1)

Kubernetes, Terraform/Pulumi execution, cloud-provider APIs, agent daemon,
multi-host scheduler, blue/green, canary, service discovery, secrets manager,
container orchestrator, package registry, dashboard, AI deployment decisions.

Mechanisms are earned by concrete failure modes or real consumer requirements —
never added because mature-looking systems have them.

## Consumers

The contract is validated by a real external consumer in a production-shaped
deployment rehearsal; `examples/static-site` (later) proves the generic
contract. Consumer specifics never leak into this repository.
